# RAG y bases vectoriales: apuntes

RAG significa generacion aumentada por recuperacion. En lugar de pedirle al modelo que
recuerde, se le traen los fragmentos relevantes y se le pide que responda solo con eso.

El pipeline tiene tres partes. Primero la ingesta: leer documentos, partirlos en chunks
y guardarlos con sus embeddings en una base vectorial. Segundo la recuperacion: convertir
la pregunta del usuario en un embedding y buscar los fragmentos mas parecidos. Tercero
la generacion: armar un prompt con esos fragmentos y pedirle al modelo una respuesta
anclada al contexto.

El chunking es el arte de partir el texto. Chunks muy chicos pierden el contexto de la
frase; chunks muy grandes diluyen el significado en el embedding. Un valor tipico es
entre 500 y 800 tokens con un solape del 10 por ciento para no cortar ideas al medio.

ChromaDB es una base vectorial local que se puede persistir en una carpeta. Se usa el
mismo modelo de embeddings para indexar y para consultar; si se mezclan modelos, las
distancias vectoriales no significan nada y la busqueda devuelve resultados aleatorios.

El top_k define cuantos fragmentos se le pasan al modelo. Si se le pasan demasiados, el
modelo se pierde en el medio del contexto y ademas se puede superar el limite de tokens.
Lo recomendado es usar entre 3 y 5.

El prompt de sistema tiene que actuar como filtro de veracidad: pedirle explicitamente
al modelo que si la respuesta no esta en el contexto, diga que no la tiene. Esto se
prueba con una pregunta trampa, cuya respuesta no este en los documentos, y se verifica
que el sistema no invente.
